# Redis 持久化


---

## 1. Redis 为什么需要持久化？

Redis 的数据存储在内存中，性能很高，但服务宕机后内存数据会丢失。

为了保证数据安全，Redis 提供了两种持久化方案：

1. **RDB**（Redis Database）
2. **AOF**（Append Only File）

生产环境一般会结合两种方式使用。


---

## 2. RDB 和 AOF 本质区别是什么？

### 2.1 RDB

- 是 Redis 某个时间点的**内存数据快照**
- 将当前内存数据生成一个**二进制文件**
- 恢复时直接加载 RDB 文件，**恢复速度快**
- 缺点：可能丢失**最近一次快照之后**的数据

### 2.2 AOF

- 记录 Redis **执行成功的写命令**
- 重启时通过重新执行 AOF 中的命令恢复数据
- **数据安全性更高**，但恢复速度相对较慢

### 2.3 对比

| 对比 | RDB | AOF |
|---|---|---|
| 存储内容 | 数据快照 | 写命令日志 |
| 文件格式 | 二进制 | 文本（混合持久化时前半可为 RDB） |
| 恢复速度 | 快 | 慢 |
| 数据安全性 | 较低 | 较高 |
| 文件大小 | 小 | 较大 |


---

## 3. 如果 RDB 和 AOF 只能选一种，选哪个？

需要根据业务场景选择。

### 3.1 选择 RDB

适用于：

- 缓存场景
- 可以接受部分数据丢失

例如：游戏排行榜、用户缓存。Redis 宕机时可接受几分钟数据丢失。

### 3.2 选择 AOF

适用于：

- 数据不能大量丢失
- 对可靠性要求高

例如：订单、支付等业务。

### 3.3 生产环境

通常采用：

> **RDB + AOF 混合持久化**

兼顾恢复速度与数据安全。


---

## 4. AOF 三种刷盘策略是什么？如何选择？

通过 `appendfsync` 控制 AOF 刷盘策略。

### 4.1 always

流程：

```text
执行写命令
    ↓
写入 AOF
    ↓
立即 fsync 刷盘
```

| | |
|---|---|
| 优点 | 数据安全最高 |
| 缺点 | 性能最低 |
| 适合 | 数据安全要求极高的场景 |

### 4.2 everysec（默认）

流程：

```text
执行写命令
    ↓
写入 AOF 缓冲区
    ↓
后台线程每秒刷盘
```

特点：

- 性能与安全折中
- 最多丢失约 **1 秒**数据
- **生产环境最常使用**

### 4.3 no

流程：

```text
执行写命令
    ↓
写入操作系统缓存
    ↓
由操作系统决定刷盘时间
```

| | |
|---|---|
| 优点 | 性能最高 |
| 缺点 | 数据丢失风险最大 |

### 4.4 推荐

生产环境一般：

```conf
appendfsync everysec
```

## 5. 为什么 Redis 先执行命令，再写 AOF？

写命令**执行成功后**，才会追加 AOF 日志。

如果先写 AOF：

```text
写入 AOF
    ↓
执行 Redis 命令失败
```

AOF 中会留下错误命令，重启重放时可能导致数据异常。

因此保证：

```text
执行成功
    ↓
追加 AOF 日志
```

保证 AOF 记录的都是有效命令。


---

## 6. AOF 重写时，子进程和主进程数据不一致怎么办？

AOF 重写会 `fork` 子进程执行；重写期间主进程仍处理客户端请求。

例如：

```text
子进程：生成新 AOF 文件
主进程：SET user Tom / SET age 20
```

主进程新增的写操作，子进程一开始并不知道。

Redis 通过 **AOF 重写缓冲区** 解决：

```text
子进程根据内存生成新 AOF
    ↓
主进程新增命令写入重写缓冲区
    ↓
子进程完成重写
    ↓
将缓冲区命令追加到新 AOF
    ↓
替换旧 AOF 文件
```

从而保证最终文件与当前数据一致。


---

## 7. RDB 执行快照时，Redis 还能修改数据吗？

**可以。**

生成 RDB 时会 `fork` 子进程做快照，主进程继续处理写请求。

为保证快照一致，使用 **Copy On Write（写时复制）**：

- 父进程修改某页数据时，复制对应内存页
- 子进程继续读取 fork 时的旧数据

因此：

> RDB 保存的是 **fork 瞬间** 的数据快照。


---

## 8. Redis RDB 如何处理过期 Key？

RDB 生成时会检查 key 是否过期：

| 情况 | 处理 |
|---|---|
| 已经过期 | **不写入** RDB 文件 |
| 未过期 | 正常保存 |

恢复 RDB 时，若发现 key 已过期，也不会加载。


---

## 9. Redis AOF 如何处理过期 Key？

AOF **不会单独**再记一份「过期时间专用结构」来表达删除；当 key 因过期被删除时，Redis 会把：

```text
DEL key
```

写入 AOF。

例如：

```text
SET user Tom EX 60
    ↓
60 秒后过期
    ↓
DEL user
    ↓
写入 AOF
```


---

## 10. Redis 主从模式中过期 Key 如何处理？

主从模式下，**不会由从节点主动删除**过期 key。

流程：

```text
主节点发现 key 过期
    ↓
删除 key
    ↓
发送 DEL 命令
    ↓
同步给从节点
```

目的：保证主从数据一致。


---

## 11. RDB 什么时候触发？

### 11.1 自动触发

配置示例：

```conf
save 900 1
save 300 10
save 60 10000
```

含义：

| 配置 | 含义 |
|---|---|
| `save 900 1` | 900 秒内至少修改 1 次 |
| `save 300 10` | 300 秒内至少修改 10 次 |
| `save 60 10000` | 60 秒内至少修改 10000 次 |

满足条件触发 `bgsave`。

### 11.2 手动触发

**save**

```text
save
```

- 同步执行
- **阻塞** Redis 主线程

**bgsave**

```text
bgsave
```

- `fork` 子进程生成 RDB
- 主线程继续处理请求

## 12. 什么是 AOF 混合持久化？

Redis 4.0 起支持 AOF 混合持久化。

开启：

```conf
aof-use-rdb-preamble yes
```

生成的 AOF 文件结构：

```text
前半部分：RDB 格式（当前数据快照）
后半部分：AOF 格式（快照之后新增的写命令）
```

优点：

- 恢复速度接近 RDB
- 数据安全性接近 AOF


---

## 13. AOF 重写是什么？为什么需要？

AOF 会随运行不断变大。例如多次覆盖同一 key：

```text
SET user Tom
SET user Jack
SET user Bob
```

最终只需保留：

```text
SET user Bob
```

**AOF 重写**：根据当前内存状态，重新生成一份更紧凑的 AOF。

作用：

1. 删除无效命令  
2. 合并重复操作  
3. 减小文件大小  
4. 提高恢复速度  


---

## 14. AOF 重写流程是什么？

```text
执行 fork
    ↓
子进程根据当前内存生成新 AOF
    ↓
主进程继续处理请求
    ↓
新增命令写入 AOF 重写缓冲区
    ↓
子进程完成重写
    ↓
追加缓冲区数据
    ↓
替换旧 AOF 文件
```


---

## 15. AOF 重写有什么缺点？

1. **磁盘占用翻倍风险**：重写期间同时存在旧 AOF 与新 AOF  
2. **fork 消耗资源**：数据量大时消耗 CPU，并增加内存压力（COW）  
3. **需维护重写缓冲区**：重写期间额外内存与合并开销  


---

## 16. Redis 7 对 AOF 有什么优化？

Redis 7 引入 **Multi Part AOF**（多部分 AOF）。

以前：

```text
appendonly.aof   # 单一大文件
```

现在更灵活地拆成：

```text
base AOF          # 基础部分
incremental AOF   # 增量部分
```

优势：

- 降低 AOF 重写压力
- 文件管理更灵活
- 提升恢复效率


---

## 17. Redis 持久化面试总结

可按下面一段组织回答：

1. Redis 持久化主要有 **RDB** 和 **AOF**。  
2. RDB 是时间点快照，恢复快，但可能丢快照后数据；AOF 记录成功写命令，可靠性更高，恢复相对慢。  
3. 生产常采用 **RDB + AOF 混合持久化**。  
4. RDB 用 **fork + Copy On Write** 保证快照一致。  
5. AOF 重写由子进程生成新文件，期间新命令进**重写缓冲区**，完成后合并并替换旧文件。  
6. 过期 Key：RDB 不保存已过期数据；AOF 用 `DEL` 记录删除；主从由主节点删除并同步从节点。
