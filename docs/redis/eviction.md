# Redis 过期策略与内存淘汰策略


---

## 1. Redis 怎么删除过期 Key？

Key 设置过期时间后，**不会立即删除**，而是采用：

> **惰性删除 + 定期删除**

两种策略结合。

### 1.1 惰性删除（Lazy Expiration）

**原理：** 客户端访问某个 Key 时，Redis 检查是否过期。

流程：

```text
GET key
    ↓
判断 key 是否过期
    ↓
若过期 → 删除 key → 返回不存在
```

例如：

```text
SET user Tom EX 60
```

60 秒后若无人访问，该 Key **仍可能留在内存中**。再次访问：

```text
GET user
```

Redis 发现已过期 → 删除 key → 返回 `nil`。

| | |
|---|---|
| 优点 | 无需主动扫描全部 Key，对 CPU 消耗较低 |
| 缺点 | 长期无人访问的过期 Key 可能一直占内存 |

### 1.2 定期删除（Periodic Expiration）

**原理：** Redis 定期执行过期 Key 清理任务。

流程：

```text
后台定时任务
    ↓
随机抽取一部分设置了 TTL 的 Key
    ↓
检查是否过期
    ↓
删除过期 Key
```

**不会扫描全部 Key。** 千万级 Key 全量扫描会造成性能问题。

策略：**随机抽样 + 时间限制**

1. 随机抽取部分带过期时间的 Key  
2. 删除其中已过期的  
3. 若发现大量过期，继续清理  
4. 达到时间限制后停止  


---

## 2. 为什么 Redis 不用单独一种过期删除策略？

| 策略 | 问题 |
|---|---|
| 只惰性删除 | 长期无人访问的过期 Key 一直占内存 |
| 只定期删除 | 扫描频率难权衡：太频繁伤性能，太少则过期 Key 堆积 |

因此采用：

> **惰性删除**保证访问时及时删除  
> **+**  
> **定期删除**保证内存不会长期浪费  


---

## 3. Redis 内存淘汰什么时候触发？

当 Redis 使用内存达到 `maxmemory` 限制时触发。

例如：

```conf
maxmemory 4GB
```

已用满 4GB 后再执行：

```text
SET key value
```

会触发内存淘汰策略。


---

## 4. Redis 有哪些内存淘汰策略？

主要分三类：

1. **不淘汰**  
2. **根据 TTL 淘汰**（volatile 系列）  
3. **根据访问情况淘汰**（allkeys 系列，含 LRU / LFU / random）

### 4.1 noeviction（不淘汰）

默认策略。超过最大内存后：

- **不删除**任何 Key  
- 新的写操作直接失败  

例如 `SET user Tom` 可能返回：

```text
OOM command not allowed
```

适合：数据不能丢失的业务。

### 4.2 volatile 系列（只淘汰设置了过期时间的 Key）

| 策略 | 含义 |
|---|---|
| `volatile-ttl` | 优先淘汰剩余 TTL 最短的 Key |
| `volatile-random` | 在设置了 TTL 的 Key 中随机删除 |
| `volatile-lru` | 在设置了 TTL 的 Key 中按 LRU 淘汰 |
| `volatile-lfu` | 在设置了 TTL 的 Key 中按 LFU 淘汰 |

`volatile-ttl` 示例：A 剩余 10 秒，B 剩余 100 秒 → 优先删 A。

### 4.3 allkeys 系列（所有 Key 参与淘汰）

| 策略 | 含义 |
|---|---|
| `allkeys-lru` | 全部 Key 按 LRU 淘汰，适合纯缓存 |
| `allkeys-lfu` | 全部 Key 按 LFU 淘汰 |
| `allkeys-random` | 随机删除任意 Key |


---

## 5. Redis 推荐使用哪种淘汰策略？

### 5.1 缓存场景

推荐：

- `allkeys-lru`
- 或 `allkeys-lfu`

原因：缓存本身允许删除，不必区分是否设置了 TTL。

### 5.2 部分 Key 不能删除

只有部分缓存设置了 TTL 时，可选：

- `volatile-lru`
- 或 `volatile-lfu`


---

## 6. Redis LRU 算法介绍

**LRU** = Least Recently Used（最近最少使用）。

核心思想：内存不足时，优先淘汰**最长时间没有被访问**的数据。

访问顺序示例：`A → B → C → D`

- 最近访问：D  
- 最久未访问：A → 淘汰 A  


---

## 7. Redis 的 LRU 是标准 LRU 吗？

**不是。** Redis 使用的是**近似 LRU**。


---

## 8. 为什么 Redis 不用标准 LRU？

标准 LRU 通常要维护完整双向链表：

```text
最新访问 ← D - C - B - A → 最久访问
```

每次访问都要调整节点位置。Key 达到千万级时会导致：

1. 大量额外内存  
2. 每次访问都要改链表  
3. 增加 CPU 开销  

因此采用近似 LRU。


---

## 9. Redis 近似 LRU 如何实现？

不维护完整访问链表，而是维护一个**淘汰候选池**。

### 9.1 基本思路

```text
随机采样部分 Key
    ↓
按空闲时间维护候选池
    ↓
多轮采样后，淘汰池中空闲时间最大的 Key
```

### 9.2 候选池更新流程

1. **首次采样**：随机采样一批 Key，根据各 Key 的**空闲时间**（idle time）加入候选池。  
2. **继续采样**：再随机采样新的 Key。  
3. **比较替换**：若新采样 Key 的空闲时间 **大于** 候选池中**空闲时间最小**的 Key，则用新 Key **替换**进入候选池（同时挤出池中空闲时间最小的那个）。  
4. **多轮之后**：从候选池中选出**空闲时间最大**的 Key 进行淘汰。

示意：

```text
随机采样一批 Key → 按空闲时间进入候选池
        ↓
继续随机采样
        ↓
新 Key 空闲时间 > 池中最小空闲时间？
        ↓ 是
替换进入候选池（淘汰池中最小空闲时间的 Key）
        ↓
多轮采样结束
        ↓
淘汰候选池中空闲时间最大的 Key
```

例如有 1000 万 Key，每轮随机抽约 **16** 个参与比较；经过多轮后，从候选池里选最“冷”的 Key 删除，在效果与性能之间取得平衡。


---

## 10. Redis LFU 算法介绍

**LFU** = Least Frequently Used（最少访问频率）。

| 算法 | 关注点 |
|---|---|
| LRU | 最近访问时间 |
| LFU | 访问次数 |

示例：

| Key | 最近访问 | 访问次数 |
|---|---|---|
| A | 10 分钟前 | 10000 |
| B | 1 分钟前 | 1 |

- LRU：更可能淘汰 A（更久未访问）  
- LFU：淘汰 B（频率更低）  


---

## 11. Redis 为什么增加 LFU？

LRU 的问题：热点数据若短时间无人访问，可能被误淘汰。

例如热点新闻刚发布访问 100 万次，一天后无人访问：

- LRU：可能因「很久没访问」而淘汰  
- LFU：因历史访问次数高，会保留更久  


---

## 12. 过期删除和内存淘汰的区别？

| | 过期删除 | 内存淘汰 |
|---|---|---|
| 触发条件 | Key 的 TTL 到期 | 达到 `maxmemory` |
| 目的 | 删除失效 Key | 释放内存 |
| 触发时机 | 访问时 / 后台定时任务 | 写入时触发 |
| 删除对象 | 过期 Key | 正常 Key 也可能被删 |
| 策略 | 惰性删除 + 定期删除 | LRU / LFU / TTL / random 等 |


---

## 13. 面试最终回答

可按下面组织：

1. Redis 删除过期 Key 采用 **惰性删除 + 定期删除**：访问时检查过期并删除；后台定时随机抽取带 TTL 的 Key 清理。  
2. 达到 `maxmemory` 时触发**内存淘汰**。  
3. 策略包括：  
   - `noeviction`：不淘汰，写入失败  
   - **volatile 系列**：只淘汰设了 TTL 的 Key（`volatile-lru` / `volatile-lfu` / `volatile-ttl` / `volatile-random`）  
   - **allkeys 系列**：所有 Key 参与（`allkeys-lru` / `allkeys-lfu` / `allkeys-random`）  
4. Redis 的 LRU 是**近似 LRU**：维护淘汰候选池，随机采样 Key 按空闲时间进出候选池，多轮后淘汰池中空闲时间最大的 Key；避免标准 LRU 维护完整链表的内存与 CPU 开销。  
5. 生产缓存场景一般选 **`allkeys-lru`** 或 **`allkeys-lfu`**。
