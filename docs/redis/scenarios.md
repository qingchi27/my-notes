# Redis 场景


---

## 1. 实际项目中 Redis 做过什么？

Redis 在项目中主要用于以下场景。

### 1.1 缓存热点数据

最常见用途。例如：用户信息、商品信息、配置信息、权限数据。

流程：

```text
请求
  ↓
查询 Redis
  ↓
命中 → 直接返回

未命中
  ↓
查询 MySQL
  ↓
写入 Redis
  ↓
返回
```

采用：**Cache Aside Pattern（旁路缓存模式）**。

### 1.2 分布式锁

多个服务节点同时操作共享资源时，用 Redis 保证互斥。

例如：防止重复提交、定时任务防重复执行、库存扣减。

加锁：

```text
SET lockKey uuid NX EX 30
```

释放：校验 value 是否为自己持有，再删除。

生产中一般使用 **Redisson**。

### 1.3 计数器

利用 Redis 原子操作，例如：

```text
INCR article:view
```

应用：浏览量、点赞数、接口访问次数。

### 1.4 排行榜

使用 ZSet。例如游戏积分：

```text
ZADD rank 100 player1
ZREVRANGE rank 0 9
```

### 1.5 秒杀库存

Redis 预扣库存：

```text
用户请求
    ↓
Redis Lua 扣库存
    ↓
MQ
    ↓
订单服务
    ↓
MySQL 落库
```

### 1.6 延迟任务

可用：

- ZSet
- Stream
- Redisson DelayQueue


---

## 2. Redis 缓存怎么应用？

典型 **Cache Aside** 模式。

### 2.1 读取

```text
查询 Redis
    ↓
存在 → 直接返回
不存在 → 查 DB → 写 Redis → 返回
```

### 2.2 更新

推荐：

```text
更新 MySQL
    ↓
删除 Redis
```

而不是「更新 MySQL → 更新 Redis」。

原因：并发下容易出现旧数据覆盖新缓存。


---

## 3. Redis 为什么适合作为 MySQL 缓存？

### 3.1 性能高

| | Redis | MySQL |
|---|---|---|
| 存储 / 执行 | 内存、单线程、IO 多路复用 | 磁盘 IO、SQL 解析、索引查询 |

Redis 访问速度远高于数据库。

### 3.2 降低数据库压力

例如 10000 次请求：

| | 查询分布 |
|---|---|
| 无缓存 | 10000 次 MySQL |
| 有缓存 | 约 9900 Redis + 100 MySQL |

### 3.3 数据结构丰富

| 类型 | 场景 |
|---|---|
| String | 缓存、计数 |
| Hash | 对象缓存 |
| List | 队列 |
| Set | 去重 |
| ZSet | 排行榜 |
| Bitmap | 签到 |


---

## 4. Redis 和 Memcached 区别？

### 4.1 共同点

- 内存缓存
- 提升访问速度
- 减少数据库压力

### 4.2 区别

| | Redis | Memcached |
|---|---|---|
| 数据结构 | 丰富 | 简单 KV |
| 持久化 | 支持 | 不支持 |
| 事务 | 支持简单事务 | 不支持 |
| Lua | 支持 | 不支持 |
| 应用范围 | 复杂业务 | 简单缓存 |

总结：Memcached 更像缓存，Redis 更像内存数据库。


---

## 5. 旁路缓存下，MySQL 更新后如何保证一致？

推荐：

```text
更新 MySQL
    ↓
删除 Redis
```

为什么不「更新缓存」？并发下易产生旧数据覆盖。

例如：

```text
线程 A：更新数据库为新数据
线程 B：查到数据库旧数据 → 写入 Redis
→ 缓存残留旧数据
```


---

## 6. 如何保证删除缓存一定成功？

无法做到 100% 一定成功，通常保证**最终一致**。

### 6.1 方案一：重试机制

删除失败 → 发 MQ → 消费者重试删除。

### 6.2 方案二：延迟双删

```text
删除缓存
    ↓
更新数据库
    ↓
等待一段时间（如 500ms）
    ↓
再次删除缓存
```

防止并发查询旧数据重新写入缓存。

### 6.3 方案三：Canal 监听 Binlog

```text
MySQL → binlog → Canal → MQ → 删除 / 更新 Redis
```

优点：业务与缓存解耦。

### 6.4 方案四：TTL 兜底

所有缓存设置过期时间；即使删除失败，最终也会失效。


---

## 7. 缓存一致性要求很高怎么办？

先区分业务强度。

### 7.1 普通业务（可接受最终一致）

```text
更新 DB → 删除缓存 → 失败则 MQ 补偿
```

### 7.2 强一致业务（钱、库存、余额等）

可选：

1. **不使用缓存**，直接查库  
2. **分布式锁**，保证同一时间只有一个线程更新  
3. **Binlog 同步**：`MySQL → Canal → MQ → 更新缓存`

核心：

> 缓存天然不是强一致系统；强一致场景优先考虑不用缓存。

## 8. 如何避免缓存失效问题？

三个经典问题：**穿透 / 击穿 / 雪崩**。

### 8.1 缓存穿透

**问题：** 查不存在的数据，Redis、MySQL 都没有，大量请求打穿到数据库。

**解决：**

1. **缓存空对象**：如 `user:100 = null`，设较短 TTL  
2. **布隆过滤器**：提前判断数据是否可能存在  
3. **参数校验**：过滤非法请求  

### 8.2 缓存击穿

**问题：** 热点 Key 过期，大量请求同时打到 DB。

**解决：**

1. **互斥锁**：一个线程查 DB，其他等待  
2. **逻辑过期**：缓存存 `data + expireTime`，过期后由后台线程刷新  

### 8.3 缓存雪崩

**问题：** 大量 Key 同时过期。

**解决：**

1. **TTL 随机化**：如 `30 分钟 + random(0~10 分钟)`  
2. **多级缓存**：`Caffeine → Redis → MySQL`  
3. **限流降级**：保护数据库

## 9. Redis 做秒杀可以吗？

可以，但 Redis 只负责**抢资格**，不负责最终订单。

### 9.1 架构

```text
用户
  ↓
Nginx 限流
  ↓
Redis Lua 扣库存
  ↓
MQ 削峰
  ↓
订单服务
  ↓
MySQL
```

### 9.2 为什么用 Lua？

「判断库存 `stock > 0`」与「扣库存 `stock--`」必须原子执行。

单纯 `DECR` 无法完整保证业务逻辑正确性。

## 10. Redis Pipeline 有什么作用？

作用：**减少网络往返（RTT）次数**，提高吞吐。

### 10.1 对比

普通：

```text
客户端 SET → 等待返回 → GET → 等待返回
```

Pipeline：

```text
一次发送多个命令 → 一次拿回一批结果
```

### 10.2 注意

- Pipeline **不保证原子性**  
- **不支持回滚**  

需要原子时使用：**Lua** 或 **Redis 事务**。

## 11. 什么是热 Key？

某个 Key 的访问量远高于其他 Key。

例如：热门商品、明星主页、热门直播。

问题：

```text
大量请求 → 打到同一个 Redis 节点 → 压力过大
```


---

## 12. 热 Key 如何发现？

1. Redis 监控：`redis-cli --hotkeys`  
2. 客户端统计 Key 访问频率  
3. 云 Redis 监控（如阿里云热 Key 分析）  


---

## 13. 热 Key 如何解决？

### 13.1 方案一：本地缓存

```text
Caffeine → Redis → MySQL
```

减少对 Redis 的直接冲击。

### 13.2 方案二：Key 拆分

```text
product:100
    ↓
product:100:1
product:100:2
...
```

随机访问副本，打散流量。

### 13.3 方案三：限流

保护 Redis，避免被打挂。


---

## 14. 什么是大 Key？

没有绝对标准，一般指：

- value 特别大  
- 集合元素特别多  

例如：String 几十 MB；Hash 几十万个 field。

危害：

1. **阻塞 Redis**（单线程，大 Key 操作耗时长）  
2. **网络压力**（传输慢）  
3. **主从同步变慢**  
4. **删除可能阻塞**  


---

## 15. 大 Key 如何排查？

| 方式 | 手段 |
|---|---|
| 在线 | `redis-cli --bigkeys` |
| 单 Key | `MEMORY USAGE key` |
| 离线 | `redis-rdb-tools` 分析 RDB |


---

## 16. 大 Key 如何解决？

### 16.1 拆分

```text
user:list
    ↓
user:list:1
user:list:2
```

### 16.2 异步删除

不要直接：

```text
DEL bigkey
```

使用：

```text
UNLINK key
```

### 16.3 渐进删除

使用 `SCAN` 分批处理。


---

## 17. Redis 事务支持回滚吗？

**不支持。**

```text
MULTI
命令...
EXEC
```

保证：命令按顺序执行。  
不保证：失败自动回滚。

原因：Redis 追求简单、高性能。需要复杂事务时用 MySQL 事务或分布式事务。


---

## 18. Redis 如何实现延迟队列？

### 18.1 方案一：ZSet

```text
key: delay_queue
score: 执行时间戳
```

消费者不断查询 `score <= 当前时间` 的元素并取出执行。

### 18.2 方案二：Redisson DelayQueue

内部基于 ZSet 等实现。

### 18.3 方案三：Stream

支持消费组、ACK，更适合可靠消费。


---

## 19. Redis 可以做消息队列吗？

可以，但有边界。

### 19.1 List

`LPUSH` + `BRPOP`：简单队列；缺点是没有 ACK。

### 19.2 Pub/Sub

实时广播；缺点是消息不持久化。

### 19.3 Stream

支持消息持久化、消费组、ACK，更适合生产。

### 19.4 什么时候用 Redis 做 MQ？

| 适合 | 不适合 |
|---|---|
| 消息量中小 | 金融交易 |
| 可靠性要求一般 | 海量消息堆积 |
| 架构简单 | 强顺序要求 |

适合示例：异步通知、日志处理、简单任务队列。

不适合时使用：**RocketMQ / Kafka / RabbitMQ**。
