# Redis 分布式锁


---

## 1. 什么是分布式锁？

分布式系统中，多个进程 / 节点对共享资源的**互斥访问**机制。

核心要求：

| 要求 | 说明 |
|---|---|
| 互斥 | 同一时刻只有一个客户端持有锁 |
| 防死锁 | 客户端崩溃后锁能自动释放 |
| 可重入（可选） | 同一线程可多次获取 |


---

## 2. Redis 为什么能实现分布式锁？

Redis 提供原子命令：

```bash
SET lock_key value NX EX 30
```

| 参数 | 含义 |
|---|---|
| `NX` | key 不存在才创建（互斥） |
| `EX` | 设置过期时间（防死锁） |

判断 + 创建 + 设过期时间，**一步原子完成**。


---

## 3. Redis 原子性原理？

1. **单线程模型**：命令串行执行，天然原子  
2. **Lua 脚本**：整个脚本作为一个命令执行，中间不插入其他请求  

注意：Lua 脚本**无回滚**，出错后已执行的命令不会撤销。


---

## 4. 分布式锁实现要点（6 条）

| 要点 | 说明 |
|---|---|
| 1. 原子加锁 | `SET NX EX`，禁止先 `GET` 再 `SET` |
| 2. 唯一 Owner | `value = UUID:threadId`，标识持有者 |
| 3. 原子解锁 | Lua：先判断 owner，再删除 |
| 4. 超时机制 | 设置过期时间，防止死锁 |
| 5. 可重入 | Hash + 计数器（Redisson 实现） |
| 6. 自动续期 | 看门狗机制，防止业务未完成锁过期 |

### 4.1 解锁 Lua 脚本

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 4.2 为什么需要 Owner？

防止 A 线程的锁超时后，B 线程获取锁，A 执行完误删 B 的锁。


---

## 5. Redis 分布式锁优缺点？

| 优点 | 缺点 |
|---|---|
| 内存操作，性能高 | 主从同步延迟：Master 宕机，锁可能丢失 |
| 实现简单 | 依赖 Redis 可用性 |
| 支持自动过期 | GC 停顿可能导致续期失败 |
| Redisson 功能完善 | 不适合强一致场景（如金融扣款） |


---

## 6. 超时时间怎么设？

原则：大于业务 **P99** 执行时间，但不过大。

推荐：

> 超时时间 ≈ P99 × 2～3

最佳实践：用 **Redisson 看门狗**自动续期，不手动设死超时。


---

## 7. Redisson 分布式锁（重点）

### 7.1 可重入锁

基于 Hash 结构：

```text
key:   lock:order:123
field: UUID:threadId
value: 重入次数（count）
```

- 加锁：`HINCRBY` count + 1  
- 解锁：`HINCRBY` count - 1，为 0 时删除 key  

### 7.2 看门狗自动续期

| 参数 | 默认值 |
|---|---|
| 锁租约时间 | 30 秒 |
| 续期周期 | 10 秒（租约的 1/3） |

流程：

1. 加锁成功后，后台启动定时任务  
2. 每 10 秒检查：锁还在且未 `unlock`，则 `PEXPIRE` 重置为 30 秒  
3. 调用 `unlock()` 后停止续期  

注意：手动指定 `leaseTime`（如 `lock(10, SECONDS)`）则**不启用**看门狗。


---

## 8. GC 停顿导致锁失效？

**问题：** Full GC 持续几十秒，看门狗线程暂停 → 锁超时 → 其他线程获取锁 → **双持锁**。

| 方案 | 说明 |
|---|---|
| 合理超时 | 默认 30 秒，一般 GC 不会这么久 |
| Fencing Token | 每次加锁带递增 token，资源服务拒绝旧 token |
| 业务幂等 | 数据库唯一索引等兜底 |
| 优化 GC | 使用 G1 / ZGC 降低 STW |


---

## 9. 集群环境下如何保证可靠？

### 9.1 问题：主从切换丢锁

```text
Master 写入锁 → 未同步到 Slave → Master 宕机 → Slave 晋升 → 锁丢失
```

### 9.2 方案对比

| 方案 | 原理 | 适用 |
|---|---|---|
| 单节点 / 哨兵 / Cluster | 常规部署 + Redisson | 绝大多数业务（默认） |
| Redlock | 5 个独立节点，过半成功才算加锁 | 极高一致性要求 |
| ZooKeeper / etcd | CP 模型，强一致 | 金融级场景 |

Redlock 有争议（时钟漂移等问题），生产主流仍用 **单 Redis + Redisson**。


---

## 10. 其他分布式锁对比？

| 方案 | 一致性 | 性能 | 特点 |
|---|---|---|---|
| Redis | AP | 高 | 简单高效，适合大多数场景 |
| ZooKeeper | CP | 中 | 临时节点自动释放，强一致 |
| etcd | CP | 中高 | Raft 协议，云原生友好 |
| MySQL | CP | 低 | 唯一索引 / 行锁，简单但性能差 |
