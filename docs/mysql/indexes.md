# 索引

## 索引核心


---

## 1. 索引分类（三维记忆法）

| 维度 | 类型 | 说明 |
|---|---|---|
| 数据结构 | B+Tree、Hash、Full-Text、Spatial | InnoDB 最常用 B+Tree |
| 逻辑功能 | 主键、唯一、普通、联合、前缀 | 按约束强度递减 |
| 存储方式 | 聚簇索引、二级索引 | 聚簇存整行，二级存「列 + 主键」 |

口诀：**数据结构选 B+，逻辑功能分五种，存储方式看聚簇二级。**


---

## 2. B+Tree 核心（为什么选它？）

### 2.1 B+Tree 四大特点

```text
① 非叶子节点只存 Key（不存数据）→ 一个节点存更多 Key
② 叶子节点存数据 → 聚簇索引存整行，二级索引存「列 + 主键」
③ 叶子节点双向链表连接 → 天然支持范围查询和排序
④ 树矮胖 → 三层可存千万级数据，减少磁盘 IO
```

### 2.2 对比：B+Tree vs B Tree vs 红黑树 vs Hash

| 对比项 | B Tree | B+Tree | 红黑树 | Hash |
|---|---|---|---|---|
| 非叶子节点 | 存 Key + Data | 只存 Key | 存数据 | 存键值对 |
| 叶子节点链表 | ❌ 无 | ✅ 有 | ❌ 无 | ❌ 无 |
| 范围查询 | 麻烦 | 极方便 | 不方便 | 不支持 |
| 树高度 | 较高 | 矮 | 高（二叉） | O(1) |
| 适用场景 | 一般索引 | 数据库首选 | 内存结构 | 等值查询 |

为什么选 B+Tree？

1. 非叶子不存数据 → 树更矮 → 减少磁盘 IO
2. 叶子链表连接 → 范围查询、排序、`BETWEEN` 极快
3. 查询效率稳定 → 每次查到叶子节点深度一致

## 3. 聚簇索引 vs 二级索引

| 特性 | 聚簇索引 | 二级索引 |
|---|---|---|
| 叶子节点内容 | 完整行数据 | 索引列 + 主键值 |
| 数量 | 通常 1 个 | 可以多个 |
| 主键查询 | 直接拿到数据 | 不需要（它就是主键） |
| 空间占用 | 较大 | 相对较小 |
| 典型例子 | `PRIMARY KEY (id)` | `INDEX idx_name(name)` |

注意：**聚簇索引 ≠ 主键索引。**

无主键时 → 选第一个唯一非 NULL 索引 → 再没有则生成隐藏 `ROW_ID`。

## 4. 回表与覆盖索引

### 4.1 回表（二次查询）

```text
查询：SELECT * FROM user WHERE name = '张三';
索引：INDEX idx_name(name)

二级索引找到 name='张三' → 得到主键 id=10 → 再去聚簇索引查完整数据
                              ↑
                           这个过程叫「回表」
```

### 4.2 覆盖索引（避免回表）

```sql
-- 查询字段全在二级索引里，无需回表
SELECT id, name FROM user WHERE name = '张三';
-- 二级索引已有 name + id，直接返回结果
```

| 场景 | 是否回表 | 优化手段 |
|---|---|---|
| `SELECT *` + 二级索引 | ✅ 回表 | 改为只查索引列，实现覆盖索引 |
| `SELECT id, name` + `INDEX(name)` | ❌ 不回表 | 本身就是覆盖索引 |

口诀：**二级索引存主键，查全字段要回表，只查索引就覆盖。**


---

## 5. 索引下推（ICP）

定义：MySQL 将部分查询条件下推给存储引擎，在索引层提前过滤，减少回表。

```sql
-- 联合索引 INDEX idx_ab(a, b)
SELECT * FROM user WHERE a = 10 AND b = 20;
```

| 阶段 | 无 ICP | 有 ICP |
|---|---|---|
| 二级索引扫描 | 找到 `a=10` 的全部记录 | 找到 `a=10` 后，继续在索引层判断 `b=20` |
| 回表次数 | 多（所有 `a=10` 都回表） | 少（仅 `b=20` 的回表） |

核心价值：**减少回表次数**，提升查询性能。

## 6. 页分裂与主键选择

### 6.1 INSERT 导致页分裂

```text
Page A: [1, 2, 3, 4, 5]  空间已满
插入 6 → 页分裂 → Page A: [1, 2, 3]  Page B: [4, 5, 6]
        ↓
   父节点索引信息也要修改
        ↓
   父节点满 → 继续向上分裂 → 甚至树高度增加
```

### 6.2 为什么推荐自增主键？

| 主键类型 | 插入方式 | 问题 |
|---|---|---|
| 自增 ID（1,2,3,4,5） | 顺序追加在 B+Tree 右侧 | ✅ 页分裂少，空间利用率高 |
| 随机 UUID（a83, 12f, f92） | 随机位置插入 | ❌ 频繁页分裂、空间碎片、缓存命中率低 |

主键设计原则：**唯一、稳定、短小、有序**

推荐：`BIGINT AUTO_INCREMENT` 或雪花算法（分布式）。

## 7. 普通索引 vs 唯一索引

| 特性 | 普通索引 | 唯一索引 |
|---|---|---|
| 允许重复 | ✅ 允许 | ❌ 不允许 |
| 唯一性检查 | 不需要 | 需要 |
| 查询性能 | 差异很小 | 差异很小 |
| 更新性能 | 差异很小 | 差异很小 |

面试答法：主要区别是**唯一性约束**，性能差异通常很小，不能简单说哪种更快。


---

## 8. 外键约束

```sql
FOREIGN KEY (user_id) REFERENCES user(id)
```

| 方面 | 说明 |
|---|---|
| 优点 | 保证引用完整性，防止孤儿数据 |
| 缺点 | 增加检查成本、表耦合、分库分表难用、影响扩展 |
| 互联网实践 | 应用层保证一致性，很少用数据库外键 |

## 9. 索引建立原则

### 9.1 适合建索引的字段

| 场景 | 例子 |
|---|---|
| 查询频繁 | `WHERE user_id = ?` |
| 区分度高 | 身份证号、订单号、用户 ID |
| 排序字段 | `ORDER BY create_time` |
| JOIN 字段 | `ON a.user_id = b.user_id` |
| 范围查询 | `WHERE create_time BETWEEN ...` |

### 9.2 不适合建索引的情况

| 场景 | 原因 |
|---|---|
| 数据量极小（如几百条以内） | 全表扫描更快 |
| 区分度极低（性别、状态） | 索引收益有限 |
| 返回大量数据（如 > 80%） | 走索引 + 回表 往往不如全表扫描 |

### 9.3 索引不是越多越好

```text
索引越多 → 查询可能更快
        → 但 INSERT / UPDATE / DELETE 更慢（需维护多个索引）
        → 占用更多磁盘和 Buffer Pool
```

原则：根据实际查询建**必要索引**，避免冗余。

## 10. 最左前缀原则（联合索引核心）

### 10.1 假设联合索引：`INDEX idx_abc(a, b, c)`

索引实际排序顺序：`a → b → c`

| SQL | 是否走索引 | 说明 |
|---|---|---|
| `WHERE a = 1` | ✅ | 命中 a |
| `WHERE a = 1 AND b = 2` | ✅ | 命中 a, b |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ | 命中 a, b, c |
| `WHERE b = 2` | ❌ | 缺少最左列 a |
| `WHERE c = 3` | ❌ | 缺少最左列 a |
| `WHERE b = 2 AND c = 3` | ❌ | 缺少最左列 a |
| `WHERE a = 1 AND c = 3` | ⚠️ 部分 | 命中 a，c 不走索引定位 |
| `WHERE a = 1 AND c = 3 AND b = 2` | ✅ | 优化器会重排顺序 |
| `WHERE a > 1 AND b = 2` | ⚠️ 部分 | a 走范围，b 可能不走 |
| `WHERE a = 1 AND b > 2 AND c = 3` | ⚠️ 部分 | a, b 走索引，c 通常不走 |

核心：不是「SQL 必须按字段顺序写」，而是「索引的**最左连续匹配**」。

优化器会自动调整条件顺序，但索引列的连续前缀必须存在。

### 10.2 联合索引设计注意事项

```text
① 字段顺序：把区分度高、查询频繁的放前面（结合实际 SQL）
② 避免冗余：有 (a,b,c) 就不需要单独建 (a)
③ 范围条件断后：范围查询后的列通常无法继续索引定位
```

## 11. 索引失效场景

| 场景 | 示例 | 解决方案 |
|---|---|---|
| 隐式类型转换 | VARCHAR 字段用数字比较 | 保持类型一致 |
| 函数操作 | `WHERE DATE(create_time) = 'xxx'` | 改为范围：`>= ... AND < ...` |
| OR 条件 | `WHERE a = 1 OR b = 2` | 看执行计划，可能 Index Merge |
| 区分度低 | `WHERE status = 1`（大部分数据） | 优化器可能选择全表扫描 |
| `SELECT *` | 导致回表过多 | 使用覆盖索引 |

重要：**有索引 ≠ 一定走索引**，最终由优化器根据成本决定。用 `EXPLAIN` 验证。

## 12. 完整知识链路（面试串讲版）

```text
为什么需要索引？
       ↓
B+Tree（为什么选它？矮、少 IO、支持范围）
       ↓
聚簇索引（叶子存整行）+ 二级索引（叶子存「列 + 主键」）
       ↓
回表（二级索引查主键再查聚簇）→ 覆盖索引（避免回表）
       ↓
联合索引 → 最左前缀原则
       ↓
索引下推 ICP（减少回表）
       ↓
页分裂（INSERT 导致）→ 为什么主键要自增有序
       ↓
索引建立原则（什么时候建、什么时候不建）
       ↓
索引失效场景 + EXPLAIN 验证
```

## 14. 核心口诀汇总

| 知识点 | 口诀 |
|---|---|
| 选 B+Tree 理由 | 矮胖少 IO，链表范围优 |
| 聚簇 vs 二级 | 聚簇存整行，二级存主键 |
| 回表与覆盖 | 二级索引存主键，查全字段要回表，只查索引就覆盖 |
| 最左前缀 | 最左连续匹配，不是 SQL 顺序 |
| 主键设计 | 唯一稳定短有序，自增整数最优选 |
| 索引原则 | 查询频繁区分高，排序 JOIN 范围好；数据少或区分低，全表扫描更划算 |
