# 高性能

## 1. 性能优化的层次

从收益通常从大到小：

1. **业务与架构**：缓存、异步、削峰、读写分离、分库分表
2. **SQL 与索引**：慢 SQL、执行计划、覆盖索引
3. **表结构设计**：字段类型、范式与反范式、主键策略
4. **参数与硬件**：Buffer Pool、磁盘、连接数

先定位瓶颈，再动手；避免一上来盲目调参。

知识链：

```text
一、SQL 性能
├── EXPLAIN 怎么看
├── Using index / Using where
├── 慢 SQL 怎么找 → 怎么优化
├── 深分页怎么优化（游标分页）
├── SQL 和索引没问题还慢怎么办
├── 索引为什么失效
├── 为什么有索引却不走
└── 怎么判断索引是否合理

二、SQL 与 NoSQL
├── SQL vs NoSQL（不要说 NoSQL 不支持事务）
└── MySQL vs MongoDB（看数据模型）

三、MySQL 主从
├── 主从复制原理（Binlog → Relay Log）
├── 复制格式（ROW 默认）vs 复制机制（异步 / 半同步 / 组复制）
├── 主从延迟原因与解决
└── 读写分离实现与延迟问题

四、MySQL 高可用
└── 主库挂了怎么办（故障检测 → 选主 → 切换 → 防脑裂）

五、分库分表
├── 什么是分库分表
├── 什么情况下分库 / 分表
└── 分库分表有什么问题（分布式 ID、跨库 JOIN、分布式事务、跨库分页 / 聚合、扩容、数据迁移）
```

## 2. 怎么看一条 SQL 是否走了索引？

使用 `EXPLAIN` 查看执行计划：

```sql
EXPLAIN SELECT * FROM user WHERE id = 1;
EXPLAIN ANALYZE SELECT ...;   -- 8.0.18+，带实际执行数据
```

重点关注：

| 字段 | 含义 |
|---|---|
| `key` | 实际使用的索引（有值说明用了索引） |
| `possible_keys` | 可能使用的索引（仅供参考） |
| `type` | 访问类型 |
| `rows` | 预计扫描行数 |
| `Extra` | `Using index`（覆盖索引）、`Using where`、`Using filesort` 等 |

`type` 大致从好到差：

```text
system > const > eq_ref > ref > range > index > ALL
```

**面试重点：`possible_keys` 有值不代表一定用索引，最终看 `key`。**

---

## 3. Extra 中 Using index 和 Using where

| Extra | 含义 |
|---|---|
| `Using index` | 覆盖索引，查询所需数据全部在索引中，不需要回表 |
| `Using where` | MySQL 还需要根据 WHERE 条件对读取的数据进行过滤 |

两者不是互斥的，可能同时出现。

```sql
SELECT id, name FROM user WHERE name = '张三';
-- 若存在 (name, id) 联合索引，所需数据全在索引中 → Using index
```

面试可以直接说：`Using index` 说明发生了覆盖索引，不需要回表；`Using where` 说明还需要进行 WHERE 条件过滤。

## 4. 怎么找慢 SQL？

三种常见方式：

**① 开启慢查询日志**

```ini
slow_query_log = ON
long_query_time = 1
```

记录执行时间超过阈值的 SQL。

**② 使用 Performance Schema**

查看 SQL 执行统计：执行次数、总耗时、平均耗时、锁等待、扫描行数。

**③ 生产环境结合监控平台**

慢 SQL 日志、数据库监控、APM、日志平台。

面试重点：慢 SQL 的发现通常依赖慢查询日志和 Performance Schema，然后再通过 `EXPLAIN` 分析具体原因。

## 5. 怎么优化慢 SQL？

建议按这个顺序回答：

**第一步：定位问题（EXPLAIN）**

- 是否走索引
- 索引是否合理
- 扫描行数是否过多
- 是否发生回表
- 是否出现 `filesort` / 临时表
- Join 是否合理
- 统计信息是否过旧（`ANALYZE TABLE`）

**第二步：优化 SQL**

- 避免 `SELECT *`，减少返回数据量
- 优化 JOIN，避免子查询不必要的重复计算
- 避免函数导致索引失效
- 避免隐式类型转换
- 避免 `%xxx` 这种无法利用普通 B+Tree 索引的条件
- 分页优化、拆大 SQL
- `IN` 列表不宜过长，可分批；批量插入用多值 `INSERT`，注意事务大小

**第三步：优化索引**

- 建立联合索引、覆盖索引
- 调整索引顺序
- 删除无效 / 冗余索引

**第四步：数据量和架构层面**

SQL 和索引已经优化仍无法满足时，再考虑：缓存、读写分离、分库分表、Elasticsearch 等专用查询系统。

### 5.1 常见改写示例

```sql
-- 坏：对列套函数
WHERE DATE(create_time) = '2024-01-01'

-- 好：范围条件
WHERE create_time >= '2024-01-01'
  AND create_time <  '2024-01-02'
```

JOIN 优化：

- 驱动表选小结果集
- 被驱动表关联列有索引
- 控制 JOIN 表数量，过深关联考虑拆分或冗余

## 6. 深分页场景如何优化？

```sql
-- 问题 SQL：OFFSET 越大，需要扫描和跳过的数据越多
SELECT * FROM user ORDER BY id LIMIT 1000000, 20;
```

**方案一：基于游标 / 上一次 ID（最优）**

```sql
SELECT * FROM user WHERE id > 1000000 ORDER BY id LIMIT 20;
```

利用索引快速定位。

**方案二：延迟关联**

```sql
SELECT * FROM user u
JOIN (
    SELECT id FROM user ORDER BY id LIMIT 1000000, 20
) t ON u.id = t.id;
```

先通过覆盖索引找到 ID，再回表查询完整数据。

**方案三：业务上限制分页深度**

例如只允许查询前 100 页。

面试最推荐：深分页核心问题是 OFFSET 越大，需要扫描和跳过的数据越多。最优方案通常是基于唯一索引使用游标分页，即 `WHERE id > lastId ORDER BY id LIMIT N`。

## 7. SQL 和索引都没问题，查询依然很慢怎么办？

这是考数据库之外的性能分析能力，不能只盯着 SQL。

| 排查方向 | 说明 |
|---|---|
| 锁等待 | SQL 本身很快，但等待锁很久。`SHOW PROCESSLIST` + InnoDB 锁信息 |
| Buffer Pool 命中率低 | 大量数据需从磁盘读取 |
| 磁盘 IO 瓶颈 | CPU、内存、磁盘不足 |
| 连接池问题 | 连接池耗尽，SQL 还没执行就在等连接 |
| 网络问题 | 数据库执行快，但网络传输大量数据 |
| 数据量过大 | 单条返回几十万甚至几百万数据，走索引也慢 |
| 数据库负载过高 | CPU 高、IO 高、活跃连接多、大量慢 SQL、大量锁竞争 |

面试总结：SQL 和索引没问题，就要从锁、IO、Buffer Pool、连接池、网络、服务器资源及数据库整体负载排查。

## 8. 索引失效、最左匹配、优化器不走索引

### 8.1 什么情况下索引会失效？

- 对索引列使用函数
- 对索引列进行计算
- 隐式类型转换
- `LIKE '%xxx'`
- 联合索引不满足最左匹配
- `OR` 使用不合理
- 数据区分度太低
- 优化器判断全表扫描成本更低

### 8.2 联合索引为什么遵循最左匹配？

因为 B+Tree 中的数据首先按照 `a` 排序，`a` 相同再按 `b` 排序，最后按 `c` 排序。必须先确定前面的列，才能有效定位后面的列。

```sql
INDEX(a, b, c)
-- 可以支持：WHERE a=?, WHERE a=? AND b=?, WHERE a=? AND b=? AND c=?
-- 通常无法有效利用：WHERE b=?
```

注意：不是「SQL 必须按字段顺序写」，而是「索引的最左连续匹配」。优化器会自动调整条件顺序，但索引列的连续前缀必须存在。

### 8.3 为什么有时候不走索引？

即使存在索引，也不一定使用。优化器会根据成本决定执行计划。

```sql
SELECT * FROM user WHERE gender = '男';
```

如果男用户占 90%，通过索引找到大量数据之后还要大量回表，可能还不如直接全表扫描。

**核心：有索引 ≠ 一定走索引。**

### 8.4 如何判断一个索引是否合理？

主要看：查询条件是否匹配、联合索引顺序是否正确、区分度是否高、查询频率、是否覆盖索引、索引大小、写入成本（索引越多写入越慢）、是否存在冗余索引。

## 9. SQL 与 NoSQL

### 9.1 SQL 和 NoSQL 有什么区别？

| 维度 | SQL | NoSQL |
|---|---|---|
| 数据模型 | 关系模型 | 文档、KV、列式等 |
| Schema | 通常结构固定 | 通常更加灵活 |
| 事务 | 通常支持 ACID | 不同产品能力不同 |
| 查询 | SQL | 各自查询方式 |
| 关联查询 | 强 | 通常较弱 |
| 扩展 | 通常更偏向纵向，也支持分布式 | 通常更强调水平扩展 |
| 典型产品 | MySQL | Redis、MongoDB |

不要简单说「SQL 支持事务，NoSQL 不支持事务」。现在很多 NoSQL 数据库也支持事务，只是能力和设计理念不同。

### 9.2 MySQL 和 MongoDB 怎么选？

核心看数据模型和业务场景，不是简单比较谁性能高。

选 MySQL：数据结构稳定、强事务要求、多表关联、复杂查询、强一致性要求。

选 MongoDB：文档型数据、Schema 灵活、嵌套结构多、对文档整体读写多、水平扩展需求明显。

面试可以说：如果业务具有明显的关系模型和事务要求，优先 MySQL；如果数据天然是文档结构、Schema 灵活、关联关系较少，可以考虑 MongoDB。

## 10. MySQL 主从复制

### 10.1 复制过程

```text
Master 执行事务
  ↓
写入 Binlog
  ↓
Slave I/O Thread 连接 Master，读取 Binlog
  ↓
写入 Slave Relay Log
  ↓
Slave SQL Thread 读取 Relay Log 并执行
  ↓
完成主从同步
```

MySQL 8.0 支持并行复制，多个 worker 提升从库应用 Relay Log 的能力。

### 10.2 几种复制模式？默认是什么？

不要死记「几种」，不同版本 / 资料对分类方式不同。也不要把下面两个维度混成一个。

**按 Binlog 记录格式：**

| 格式 | 说明 |
|---|---|
| SBR（Statement-based） | 记录 SQL 语句 |
| RBR（Row-based） | 记录具体数据行变化。MySQL 5.7.7+ 默认 |
| MBR（Mixed-based） | 按 SQL 情况自动选择 |

ROW 模式记录具体数据行变化，能够避免 Statement 模式下由于函数、非确定性操作造成的主从不一致。

**按复制确认机制 / 架构：**

- 异步复制
- 半同步复制
- Group Replication

## 11. 主从延迟与读写分离

### 11.1 主从复制延迟怎么解决？

主从复制是异步的，存在延迟是正常现象。

常见原因：从库性能不足、主库写入量太大、从库 SQL Thread 执行能力不足、大事务、磁盘 IO 瓶颈、网络问题、从库存在大量查询占用资源。

优化：

1. 并行复制（多 worker）
2. 避免大事务（拆分）
3. 提升从库硬件（CPU、内存、SSD）
4. 减少从库压力（避免从库承担大量复杂查询）
5. 架构层面：强一致性要求的数据直接读主库；允许最终一致的读从库

```text
写入订单 / 刚写完立刻查订单 → Master
查询商品列表（允许最终一致） → Slave
```

### 11.2 读写分离怎么实现？

MySQL 本身只负责主从复制，不会自动完成业务层面的读写路由。通常通过中间件或应用层实现：

```text
          ┌── Master ← 写
Application
          └── Slave  ← 读
```

常见方案：ShardingSphere、MySQL Router、ProxySQL、应用层数据源路由。

核心逻辑：写请求发送主库，读请求发送从库。

实际生产还要考虑主从延迟：刚写完马上读从库，可能读不到刚写的数据。解决：强制读主、延迟检测、会话粘滞、GTID / 位点判断、中间件路由策略。

## 12. 主库挂了怎么办？

不能简单回答「把 Slave 提升成 Master」。完整流程：

```text
Master 故障
  ↓
监控 / 高可用组件发现
  ↓
选举新的 Master
  ↓
提升 Slave
  ↓
修改路由
  ↓
应用连接新 Master
```

常见方案：MHA、Orchestrator、MySQL InnoDB Cluster、云数据库高可用。

核心需要解决：

| 环节 | 说明 |
|---|---|
| 故障检测 | 判断 Master 是否真正故障 |
| 选主 | 从多个 Slave 中选择数据最完整、复制延迟最小的节点 |
| 数据一致性 | 尽量减少数据丢失 |
| 流量切换 | 让应用连接新的 Master |
| 防止脑裂 | 避免旧 Master 恢复后继续接收写请求 |

面试总结：主库故障需要通过高可用组件进行故障检测、选主、主从切换和流量重路由，同时处理复制延迟、数据丢失和脑裂问题。

## 13. 分库分表

### 13.1 什么是分库分表？

将原来一个数据库中的数据拆分到多个数据库或多个表。

```text
原来：DB → user

拆分后：
DB1 → user_0, user_1
DB2 → user_2, user_3
```

单表数据量很大（经验上常到千万～亿级，且查询变慢）时再评估，不要过早拆分。

### 13.2 什么时候分表？什么时候分库？

| | 分表 | 分库 |
|---|---|---|
| 解决 | 单表数据量过大 | 单库资源和并发瓶颈 |
| 场景 | 单表数据量大、索引膨胀、查询性能下降、数据增长很快 | CPU / IO / 连接数 / 存储瓶颈、单库写入压力太大 |

**最好记一句：分表主要解决单表数据量问题，分库主要解决单库资源和并发瓶颈。** 实际生产中经常一起使用：分库分表。

### 13.3 拆分方式

| 方式 | 含义 | 场景 |
|---|---|---|
| 垂直分库 | 按业务拆库 | 用户库 / 订单库解耦 |
| 垂直分表 | 按列拆表 | 冷热字段分离 |
| 水平分库分表 | 按行拆分 | 单表过大、写入瓶颈 |

水平拆分常用策略：按 `user_id` 取模、按时间范围（订单按月）、一致性哈希（扩容更友好）。

### 13.4 分库分表后会产生什么问题？怎么解决？

这是分库分表最核心的题。

| 问题 | 说明 | 解决方案 |
|---|---|---|
| 分布式 ID | 原来的 `AUTO_INCREMENT` 只能保证单库内唯一 | UUID、雪花算法、数据库号段模式。Java 后端重点掌握：雪花算法 + 号段模式 |
| 跨库 JOIN | 两个表可能不在同一个数据库 | 尽量避免跨库 JOIN、应用层聚合、数据冗余、ES 等查询系统、合理设计分片键 |
| 分布式事务 | 涉及多个数据库 | 尽量避免、最终一致性、本地消息表、MQ、Seata、TCC |
| 跨库分页 / 排序 | 各库各取 Top N，再合并 | 应用层合并排序（额外网络和计算开销） |
| 跨库聚合 | `COUNT` / `SUM` / `AVG` / `GROUP BY` | 各库执行后汇总 |
| 扩容问题 | `user_id % 4` 扩到 `% 8` 时大量数据重新分布 | 一致性哈希、虚拟槽、预分片、合理分片策略、成熟中间件 |
| 数据迁移 | 扩容或修改分片规则 | 历史数据迁移、增量同步、双写、数据校验、灰度切换 |

## 14. 表结构与字段设计

1. 选更小的合适类型：`TINYINT` 能表示就别用 `INT`
2. 金额用 `DECIMAL`
3. 字符集统一 `utf8mb4`
4. 尽量 `NOT NULL` + 默认值
5. 主键尽量有序
6. 适度冗余字段，换取避免高频多表 JOIN
7. 大字段（文本 / JSON）与热点查询列分离，必要时垂直拆分

## 15. 缓存与连接参数

### 15.1 缓存（常与 Redis 配合）

适用：读多写少、允许短暂不一致的热点数据。

注意经典问题：

- 缓存穿透：查不存在的数据
- 缓存击穿：热点 key 过期
- 缓存雪崩：大量 key 同时过期

### 15.2 连接与内存参数（认知即可）

| 参数 | 作用 |
|---|---|
| `innodb_buffer_pool_size` | InnoDB 最重要缓存，通常可设为机器内存较大比例 |
| `max_connections` | 最大连接数，过大可能拖垮内存 |
| `innodb_flush_log_at_trx_commit` / `sync_binlog` | 安全与性能权衡 |
| 连接池 | 应用侧用 HikariCP 等复用连接，避免频繁建连 |

原则：先保证慢 SQL 与索引正确，再谈参数微调。Buffer Pool 是 InnoDB 性能心脏。

### 15.3 批量与事务性能

1. 单条提交改为批量提交（控制批次，如 500～2000）
2. 避免超大事务（回滚慢、锁久、undo 膨胀）
3. 导入可用临时关二级索引 / 合理调整参数，但生产变更要谨慎
4. 热点行更新（同一行高频改）是瓶颈，考虑拆分热点、队列化、缓冲汇总

## 16. 诊断清单（实战）

1. CPU 高：是否大量全表扫描、排序、临时表？
2. IO 高：Buffer Pool 是否过小？磁盘是否瓶颈？刷脏是否太猛？
3. 锁等待：是否无索引更新、长事务、间隙锁冲突？
4. 连接打满：是否慢 SQL 占连接、连接池泄漏、突发流量？
5. 主从延迟：大事务、从库硬件不足、并行复制配置？

## 17. 面试速答

### 17.1 怎么优化一条慢 SQL？

先 `EXPLAIN` 看是否走索引、扫描行数、是否回表 / filesort / 临时表；再改 SQL（避免 `SELECT *`、函数、隐式转换、`%xxx`）；再优化索引（联合索引、覆盖索引、删冗余）；还不够再上架构（缓存、读写分离、分库分表）。

### 17.2 深分页怎么优化？

OFFSET 越大越慢。最优方案是基于唯一索引的游标分页：`WHERE id > lastId ORDER BY id LIMIT N`。也可以延迟关联先查 ID 再回表，或业务限制分页深度。

### 17.3 SQL 和索引都没问题还慢？

从锁等待、Buffer Pool、磁盘 IO、连接池、网络、返回数据量、数据库整体负载继续排查，不能只盯着 SQL。

### 17.4 主库挂了怎么办？

通过高可用组件做故障检测、选主、主从切换和流量重路由，同时处理复制延迟、数据丢失和脑裂。不能只说「把 Slave 提升成 Master」。

### 17.5 分库分表后有什么问题？

分布式 ID、跨库 JOIN、分布式事务、跨库分页 / 聚合、扩容、数据迁移。分表解决单表数据量，分库解决单库资源和并发瓶颈。

### 17.6 速记清单

1. 优化顺序：架构 → SQL / 索引 → 表结构 → 参数
2. `EXPLAIN` 看 `type` / `key` / `rows` / `Extra`
3. 深分页、索引失效、乱序主键是高频坑
4. 读写分离要处理延迟；分库分表不要过早
5. Buffer Pool 是 InnoDB 性能心脏
6. 有索引 ≠ 一定走索引；不要说 NoSQL 不支持事务
