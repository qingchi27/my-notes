# 高性能

## 1. 性能优化的层次

从收益通常从大到小：

1. **业务与架构**：缓存、异步、削峰、读写分离、分库分表
2. **SQL 与索引**：慢 SQL、执行计划、覆盖索引
3. **表结构设计**：字段类型、范式与反范式、主键策略
4. **参数与硬件**：Buffer Pool、磁盘、连接数

先定位瓶颈，再动手；避免一上来盲目调参。


---

## 2. 慢查询分析流程

### 2.1 发现慢 SQL

- 开启 `slow_query_log`
- 监控（Prometheus / 云监控 / RDS 控制台）
- 应用侧耗时埋点

### 2.2 看执行计划

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1 AND status = 1;
EXPLAIN ANALYZE SELECT ...;   -- 8.0.18+，带实际执行数据
```

关注字段：

| 字段 | 关注点 |
|---|---|
| `type` | 访问类型，至少避免 `ALL` |
| `key` | 实际用到的索引 |
| `rows` | 预估扫描行数 |
| `Extra` | filesort / temporary / 是否覆盖索引 |

`type` 大致从好到差：

```text
system > const > eq_ref > ref > range > index > ALL
```

### 2.3 优化动作

1. 加/改联合索引
2. 改写 SQL（避免函数破坏索引、减少 `SELECT *`）
3. 分页优化、拆大 SQL
4. 确认统计信息是否过旧（`ANALYZE TABLE`）


---

## 3. 常见 SQL 优化点

### 3.1 避免选错索引 / 失效

```sql
-- 坏：对列套函数
WHERE DATE(create_time) = '2024-01-01'

-- 好：范围条件
WHERE create_time >= '2024-01-01'
  AND create_time <  '2024-01-02'
```

### 3.2 深分页

```sql
-- 坏：越大越慢
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 好：延迟关联
SELECT o.*
FROM orders o
JOIN (
  SELECT id FROM orders ORDER BY id LIMIT 1000000, 20
) t ON o.id = t.id;

-- 更好：基于上次最大 id 的游标翻页
SELECT * FROM orders WHERE id > 123456 ORDER BY id LIMIT 20;
```

### 3.3 JOIN 优化

- 驱动表选小结果集
- 被驱动表关联列有索引
- 控制 JOIN 表数量，过深关联考虑拆分或冗余

### 3.4 只查需要的列

减少回表与网络传输；能覆盖索引更好。

### 3.5 IN 与批量

- `IN` 列表不宜过长，可分批
- 批量插入用多值 `INSERT`，注意事务大小

## 4. 表结构与字段设计

1. 选更小的合适类型：`TINYINT` 能表示就别用 `INT`
2. 金额用 `DECIMAL`
3. 字符集统一 `utf8mb4`
4. 尽量 `NOT NULL` + 默认值
5. 主键尽量有序
6. 适度冗余字段，换取避免高频多表 JOIN
7. 大字段（文本/JSON）与热点查询列分离，必要时垂直拆分


---

## 5. 缓存与读写分离

### 5.1 缓存（常与 Redis 配合）

适用：读多写少、允许短暂不一致的热点数据。

注意经典问题：

- 缓存穿透：查不存在的数据
- 缓存击穿：热点 key 过期
- 缓存雪崩：大量 key 同时过期

### 5.2 读写分离

- 主库写，从库读
- 注意主从延迟导致的“写后即读”不一致
- 关键读可走主库，或会话级强制读主


---

## 6. 分库分表（何时考虑）

单表数据量很大（经验上常到千万～亿级，且查询变慢）时再评估，不要过早拆分。

### 6.1 拆分方式

| 方式 | 含义 | 场景 |
|---|---|---|
| 垂直分库 | 按业务拆库 | 用户库 / 订单库解耦 |
| 垂直分表 | 按列拆表 | 冷热字段分离 |
| 水平分库分表 | 按行拆分 | 单表过大、写入瓶颈 |

### 6.2 水平拆分常用策略

- 按 user_id 取模
- 按时间范围（订单按月）
- 一致性哈希（扩容更友好）

### 6.3 带来的问题

- 跨库 JOIN 困难
- 分布式事务复杂
- 全局有序 ID、分页、统计更难

常见方案：业务解耦、冗余、汇总表、中间件（ShardingSphere 等）。


---

## 7. 连接与内存参数（认知即可）

| 参数 | 作用 |
|---|---|
| `innodb_buffer_pool_size` | InnoDB 最重要缓存，通常可设为机器内存较大比例 |
| `max_connections` | 最大连接数，过大可能拖垮内存 |
| `innodb_flush_log_at_trx_commit` / `sync_binlog` | 安全与性能权衡 |
| 连接池 | 应用侧用 HikariCP 等复用连接，避免频繁建连 |

原则：先保证慢 SQL 与索引正确，再谈参数微调。


---

## 8. 批量与事务性能

1. 单条提交改为批量提交（控制批次，如 500～2000）
2. 避免超大事务（回滚慢、锁久、undo 膨胀）
3. 导入可用临时关二级索引/合理调整参数，但生产变更要谨慎
4. 热点行更新（同一行高频改）是瓶颈，考虑拆分热点、队列化、缓冲汇总


---

## 9. 诊断清单（实战）

1. CPU 高：是否大量全表扫描、排序、临时表？
2. IO 高：Buffer Pool 是否过小？磁盘是否瓶颈？刷脏是否太猛？
3. 锁等待：是否无索引更新、长事务、间隙锁冲突？
4. 连接打满：是否慢 SQL 占连接、连接池泄漏、突发流量？
5. 主从延迟：大事务、从库硬件不足、并行复制配置？


---

## 10. 面试速记

1. 优化顺序：架构 → SQL/索引 → 表结构 → 参数
2. `EXPLAIN` 看 `type` / `key` / `rows` / `Extra`
3. 深分页、索引失效、乱序主键是高频坑
4. 读写分离要处理延迟；分库分表不要过早
5. Buffer Pool 是 InnoDB 性能心脏
