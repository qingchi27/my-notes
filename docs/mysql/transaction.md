# 事务

## 1. 什么是事务？

事务是一组要么全部成功、要么全部失败的 SQL 操作单元，用来保证业务一致性。

典型例子：转账

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- 出错则 ROLLBACK;
```


---

## 2. ACID 速记（各靠什么保证）

| 特性 | 英文 | 核心含义 | 实现机制 |
|---|---|---|---|
| 原子性 | Atomicity | 要么全成功，要么全回滚 | Undo Log |
| 一致性 | Consistency | 事务前后约束和业务规则不被破坏 | 约束 + 事务机制综合保证 |
| 隔离性 | Isolation | 事务中间状态对其他事务不可见 | 锁 + MVCC |
| 持久性 | Durability | 提交后宕机不丢数据 | Redo Log + WAL |

口诀：**Undo 原子 Redo 久，隔离靠锁加 MVCC。**


---

## 3. 两大日志在事务中的分工

| 日志 | 事务中的作用 | 核心场景 |
|---|---|---|
| Undo Log | 保存修改前的数据，用于回滚 | 事务失败 / 主动 `ROLLBACK` 时恢复旧值 |
| Redo Log | 记录修改后的数据，用于崩溃恢复 | 宕机后根据日志重做已提交事务 |

### WAL（Write-Ahead Logging）

```text
UPDATE 数据
    ↓
先写 Undo Log（以备回滚）
    ↓
再写 Redo Log（先落盘）
    ↓
事务提交（此时数据页可能在内存，未刷盘）
    ↓
后台异步刷脏页到磁盘
```

核心思想：**先写日志，再写数据**。提交时保证日志已持久化，数据页可以慢慢刷。

## 4. 事务开启方式

```sql
-- 显式事务
START TRANSACTION;   -- 或 BEGIN;
-- SQL...
COMMIT;
-- 或 ROLLBACK;

-- 自动提交（默认开启）
SHOW VARIABLES LIKE 'autocommit';
SET autocommit = 0;
```

注意：

- DDL（如 `ALTER TABLE`）通常会隐式提交
- 长事务会占用 undo、锁资源，应尽量短小

## 5. 隔离级别与三大并发问题

### 5.1 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| RU（Read Uncommitted） | ❌ | ❌ | ❌ | 几乎不用 |
| RC（Read Committed） | ✅ | ❌ | ❌ | 部分互联网业务选用 |
| RR（Repeatable Read） | ✅ | ✅ | ✅ | **MySQL 默认** |
| Serializable | ✅ | ✅ | ✅ | 串行化，性能极低 |

> 表中 ✅ = 能防止，❌ = 不能防止。

记忆：**RU 全不防，RC 防脏读，RR 防脏读+不可重复读，Serializable 全防但最慢。**

查看 / 设置：

```sql
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 5.2 三大问题定义（必须分清）

| 问题 | 定义 | 关注点 |
|---|---|---|
| 脏读 | 读到其他事务未提交的数据 | 数据是「临时」的，对方可能回滚 |
| 不可重复读 | 同一事务内两次读同一条记录，结果不同 | 单条记录的值变了 |
| 幻读 | 同一事务内两次按条件查询，结果集行数不同 | 记录集合多了 / 少了行 |

关键区分：**不可重复读是「一条记录数据变了」，幻读是「符合条件的行数变了」。**

## 6. MVCC 核心机制（多版本并发控制）

### 6.1 是什么？

同一条数据保存多个历史版本，不同事务读取自己应该看到的版本，减少读写锁竞争。

### 6.2 三大支柱

| 组件 | 作用 |
|---|---|
| 隐藏字段 | 每行记录隐含 `DB_TRX_ID`（最近修改事务 ID）、`DB_ROLL_PTR`（回滚指针） |
| Undo Log | 形成版本链：当前版本 → 历史版本 → 更早版本 |
| Read View | 事务快照读时生成的「可见性视图」，判断哪个版本对当前事务可见 |

补充：无主键时还有隐藏行号 `DB_ROW_ID`。

### 6.3 版本链示意

```text
当前版本: money=900, trx_id=200
              ↓ roll_pointer
历史版本: money=1000, trx_id=100
              ↓ roll_pointer
更早版本: money=1100, trx_id=50
```

### 6.4 可见性判断规则（简化版）

```text
1. 版本 trx_id 等于当前事务 ID → 可见（自己改的）
2. 版本 trx_id 在 Read View 创建前已提交 → 可见
3. 版本 trx_id 在 Read View 创建时仍活跃（未提交）→ 不可见
4. 不可见时沿 roll_pointer 找上一个版本，继续判断
```

## 7. RC vs RR 的 MVCC 核心区别

| 对比项 | RC（Read Committed） | RR（Repeatable Read） |
|---|---|---|
| Read View 创建时机 | 每次 SELECT 都创建新的 | 事务第一次 SELECT 时创建，之后复用 |
| 能看到其他事务提交 | 能（每次读最新已提交） | 不能（始终看快照时的状态） |
| 不可重复读 | 存在 | 解决 |
| 幻读（快照读） | 存在 | MVCC 解决 |
| 幻读（当前读） | 存在 | Next-Key Lock 解决 |
| 间隙锁使用 | 较少 | 较多（防幻读需要） |

口诀：**RC 每次新建视图，RR 一视到底。**


---

## 8. RR 如何解决幻读？（双机制）

必须区分两种读方式。

### 8.1 快照读（普通 SELECT）

```sql
SELECT * FROM user WHERE age > 20;
```

- 机制：MVCC + Read View
- 原理：事务内复用同一个 Read View，其他事务插入的新版本对当前事务不可见
- 结果：两次查询结果集一致

### 8.2 当前读（加锁读）

```sql
SELECT * FROM user WHERE age > 20 FOR UPDATE;
SELECT * FROM user WHERE age > 20 LOCK IN SHARE MODE;
```

- 机制：Next-Key Lock = Record Lock（记录锁）+ Gap Lock（间隙锁）
- 原理：不仅锁住已有记录，还锁住记录之间的间隙，阻止其他事务插入
- 结果：防止「幻影行」出现

面试金句：**RR 下，快照读靠 MVCC，当前读靠 Next-Key Lock。**

### 8.3 RR 有没有完全解决幻读？

不能说「完全解决」。

标准并发事务场景下，InnoDB 通过上述双机制有效避免幻读。但如果涉及：

- 事务中先快照读后当前读混用
- 特定隔离机制边界情况

仍可能出现不一致。面试时强调「区分快照读和当前读」比背「完全解决」更得分。

## 9. 为什么部分互联网业务选 RC？

MySQL 默认是 RR，但部分高并发业务主动改为 RC：

| 原因 | 说明 |
|---|---|
| 并发性能更好 | 每次读最新已提交数据，事务间隔离更弱，锁竞争减少 |
| 减少间隙锁 | RC 下间隙锁使用范围更小，降低死锁概率 |
| 业务可接受 | 部分业务对「不可重复读」不敏感，更追求吞吐量 |

注意：不是「所有互联网公司都用 RC」，需结合业务场景。

## 10. 长事务的五大弊端

```sql
BEGIN;
-- SQL1 ~ SQL10000
COMMIT;
```

| 弊端 | 原因 | 后果 |
|---|---|---|
| 锁持有时间长 | 事务不结束，锁不释放 | 其他事务阻塞，并发下降 |
| Undo Log 膨胀 | 大量修改产生大量回滚日志 | 磁盘空间增长，性能下降 |
| 历史版本无法清理 | 长事务持有旧 Read View | MVCC 旧版本堆积 |
| 死锁概率增加 | 持有锁多、时间长 | 不同事务加锁顺序冲突 |
| 回滚成本高 | 失败时需回滚大量操作 | `ROLLBACK` 极慢 |

建议：事务尽量短小精悍，避免大事务。

## 11. MySQL 事务 vs Redis 事务

| 特性 | MySQL 事务 | Redis 事务（MULTI/EXEC） |
|---|---|---|
| ACID | 完整支持 | 不保证完整 ACID |
| 回滚机制 | Undo Log 支持回滚 | 不支持自动回滚（某条失败不影响其他） |
| 隔离机制 | MVCC + 锁 + 隔离级别 | 仅保证命令按顺序执行，中间不插入其他客户端命令 |
| 崩溃恢复 | Redo Log + Binlog | 无传统数据库恢复机制 |
| 本质 | 完整数据库事务模型 | 命令批量打包执行 |

## 12. 事务使用建议

1. 事务尽可能短，避免长事务拖垮 undo / purge
2. 事务内少做远程调用、少做无关计算
3. 捕获异常后明确 `ROLLBACK`
4. 合理选择隔离级别：金融强一致可 RR；高并发读多写少可评估 RC
5. Spring 中注意传播行为、自调用导致事务失效等问题（见 SSM 事务笔记）

## 13. 面试核心主线（必须能串讲）

```text
MySQL 事务
    │
    ├── ACID
    │   ├── 原子性 → Undo Log（回滚）
    │   ├── 一致性 → 约束 + 机制综合
    │   ├── 隔离性 → 锁 + MVCC
    │   └── 持久性 → Redo Log + WAL
    │
    ├── 隔离级别
    │   ├── RU → 什么都不防
    │   ├── RC → 防脏读（每次新建 Read View）
    │   ├── RR → 防脏读 + 不可重复读（复用 Read View）
    │   └── Serializable → 全防，串行
    │
    ├── 三大问题
    │   ├── 脏读 → 读到未提交数据
    │   ├── 不可重复读 → 同一条记录两次读不同
    │   └── 幻读 → 结果集行数变化
    │
    ├── MVCC
    │   ├── 隐藏字段（trx_id, roll_ptr）
    │   ├── Undo Log（版本链）
    │   └── Read View（可见性判断）
    │
    ├── RR 解决幻读
    │   ├── 快照读（普通 SELECT）→ MVCC
    │   └── 当前读（FOR UPDATE）→ Next-Key Lock
    │
    └── 长事务危害
        ├── 锁持有久
        ├── Undo 膨胀
        ├── 版本无法清理
        ├── 死锁概率高
        └── 回滚成本高
```
