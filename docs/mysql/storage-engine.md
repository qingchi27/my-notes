# 存储引擎

## 1. SQL 执行全流程（5 步）

```text
客户端 → [连接器] → [解析器] → [优化器] → [执行器] → [存储引擎] → 数据
         建连认证    词法语法    选执行计划   调用引擎     读写数据
```

| 阶段 | 核心职责 | 记忆关键词 |
|---|---|---|
| 连接器 | TCP 连接、用户名密码认证、权限校验 | 连 |
| 解析器 | 词法分析、语法分析、生成解析树 | 解 |
| 优化器 | 根据统计信息选择最优执行计划（索引、连接顺序） | 优 |
| 执行器 | 按执行计划调用存储引擎接口 | 执 |
| 存储引擎 | 真正负责数据的物理读写（InnoDB / MyISAM 等） | 存 |

一句话：**Server 层**负责 SQL 的解析、优化和执行；**存储引擎**负责数据的实际存储和读写。

补充：MySQL 8.0 已移除 Query Cache。

## 2. 存储引擎对比

### 2.1 常见引擎速览

| 引擎 | 事务 | 行级锁 | MVCC | 适用场景 | 现状 |
|---|---|---|---|---|---|
| InnoDB | ✅ | ✅ | ✅ | 高并发 OLTP | 默认引擎，生产主流 |
| MyISAM | ❌ | ❌ | ❌ | 读多写少、无事务需求 | 逐渐淘汰 |
| Memory | ❌ | ❌ | ❌ | 临时表、高速缓存 | 内存存储，重启丢失 |
| Archive | ❌ | ❌ | ❌ | 日志、归档数据 | 高压缩，只支持 INSERT / SELECT |
| CSV | ❌ | ❌ | ❌ | 数据交换 | 文本格式存储 |

### 2.2 InnoDB vs MyISAM 核心差异

| 特性 | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 ACID | 不支持 |
| 锁粒度 | 行级锁 | 表级锁 |
| MVCC | 支持 | 不支持 |
| 聚簇索引 | 支持 | 不支持 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 强（Redo Log） | 弱 |
| 并发写性能 | 好 | 差 |

口诀：**事务行锁 MVCC，聚簇外键能恢复** —— 全是 InnoDB 的强项。

## 3. 为什么选择 InnoDB？（6 大理由）

| 理由 | 核心能力 | 典型场景 |
|---|---|---|
| 1. 事务 | ACID 保证，要么全成功要么全回滚 | 转账：A 扣 100，B 加 100 |
| 2. 行级锁 | 只锁目标行，不锁整张表 | 高并发 UPDATE |
| 3. MVCC | 读写不阻塞，普通 SELECT 不加锁 | RR 隔离级别下的一致性读 |
| 4. 聚簇索引 | 主键索引叶子节点直接存整行数据 | 主键查询极快 |
| 5. 崩溃恢复 | Redo Log 保证已提交数据不丢失 | 宕机后自动恢复 |
| 6. 外键 | 支持引用完整性约束 | 需要强一致关联的场景 |

一句话：互联网业务需要 **事务 + 高并发 + 行锁 + MVCC + 崩溃恢复**，InnoDB 全满足。

## 4. 索引核心概念

### 4.1 聚簇索引（Clustered Index）

- **定义**：叶子节点直接存储完整的行数据
- **默认**：主键就是聚簇索引
- **无主键时**：选第一个唯一非 NULL 索引 → 否则生成隐藏 `ROW_ID`

```text
        B+Tree 结构示意
           [10]
          /    \
        [5]    [15]
        / \    / \
      ... ... ... ...

叶子节点存储：id=1, name=张三, age=20  ← 完整行数据
```

为什么推荐自增主键？

自增 ID（1,2,3,4,5）顺序插入，减少页分裂和随机 IO，性能更好。

### 4.2 二级索引与回表

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,      -- 聚簇索引
  name VARCHAR(50),
  age INT,
  INDEX idx_name(name)        -- 二级索引
);
```

二级索引叶子节点存储：**索引列值 + 主键值**。

```text
查询：SELECT * FROM user WHERE name = '张三';

二级索引 idx_name              聚簇索引
   张三 → id=10  ──────────→   id=10 → 完整数据
        ↑
      得到主键                  回表查完整数据
```

| 概念 | 含义 | 优化方向 |
|---|---|---|
| 回表 | 二级索引查到主键后，再去聚簇索引查完整数据 | 减少回表次数 |
| 覆盖索引 | 查询字段全在二级索引里，无需回表 | 如 `SELECT id, name` 只需二级索引 |

口诀：**二级索引存「索引列 + 主键」，查全字段要回表，只查索引列就覆盖。**

## 5. NULL / CHAR / VARCHAR

### 5.1 NULL

- **含义**：未知 / 不存在 / 没有值（≠ `0`，≠ `''`，≠ `'NULL'`）
- **比较**：必须用 `IS NULL` / `IS NOT NULL`，不能用 `= NULL`
- **存储**：InnoDB 使用 **NULL bitmap** 标识哪些字段为 NULL（不是固定 1 字节）
  - 空间大致与可 NULL 列数量有关：约 `可 NULL 列数 / 8` 向上取整到字节

### 5.2 CHAR vs VARCHAR

| 特性 | CHAR | VARCHAR |
|---|---|---|
| 长度 | 定长 | 变长 |
| 空间 | 固定分配，可能浪费 | 按实际长度 + 额外长度信息 |
| 适用场景 | 手机号、状态码、固定编码 | 姓名、地址、标题、描述 |
| 例子 | `CHAR(10)` | `VARCHAR(255)` |

注意：`VARCHAR(255)` 的 `255` 是**字符数上限**，不是字节数。

## 6. Buffer Pool（缓冲池）

### 6.1 是什么？

InnoDB 在内存中开辟的缓存区域，缓存**数据页**和**索引页**，减少磁盘 IO。

### 6.2 数据访问流程

```text
有缓存：  Buffer Pool → 直接返回（内存读取，极快）
无缓存：  磁盘 → Buffer Pool → 返回数据
```

### 6.3 修改数据流程（WAL 思想）

```text
磁盘数据页 → 加载到 Buffer Pool → 修改内存页 → 成为 Dirty Page
                                                    ↓
                                              Redo Log 持久化
                                                    ↓
                                              事务提交
                                                    ↓
                                              后台异步刷脏页 → 磁盘
```

核心：修改先写**内存 + Redo Log**，不是立刻刷盘，后台异步完成。

## 7. 三大日志（面试必考）

### 7.1 速查表

| 日志 | 所属层级 | 类型 | 核心作用 | 记忆口诀 |
|---|---|---|---|---|
| Redo Log | InnoDB 存储引擎 | 物理日志（数据页变化） | 持久性 + 崩溃恢复 | 先写日志再写盘 |
| Undo Log | InnoDB 存储引擎 | 逻辑日志 | 回滚 + MVCC | 保存历史版本 |
| Binlog | MySQL Server 层 | 逻辑日志（SQL / 行变更） | 主从复制 + 数据恢复 | 主从同步靠它 |

### 7.2 Redo Log vs Binlog

| 对比项 | Redo Log | Binlog |
|---|---|---|
| 所属 | InnoDB | MySQL Server |
| 内容 | 数据页的物理变化 | SQL / 行的逻辑变更 |
| 用途 | 崩溃恢复 | 主从复制、时间点恢复 |
| 写入方式 | 循环写（固定空间） | 追加写（持续生成新文件） |
| 是否可替代 | ❌ 不能替代 Binlog | ❌ 不能替代 Redo Log |

为什么两者都要？

- Redo Log 解决 InnoDB 自己的**崩溃恢复**
- Binlog 解决**主从复制**和**数据恢复**

问题域不同，缺一不可。

### 7.3 两阶段提交（2PC）

事务提交时，保证 Redo Log 和 Binlog 一致：

```text
修改 Buffer Pool
     ↓
写 Undo Log
     ↓
写 Redo Log（prepare 阶段）
     ↓
写 Binlog
     ↓
Redo Log（commit 阶段）
     ↓
事务提交完成
```

目的：防止 Redo Log 和 Binlog 不一致，导致主从数据不一致或恢复结果错误。

```text
        SQL 语句

          ↓
    ┌─────────────┐
    │   InnoDB    │

```

## 9. 核心口诀速记

| 知识点 | 口诀 |
|---|---|
| SQL 执行流程 | 连解优执存 |
| 选 InnoDB 理由 | 事务行锁 MVCC，聚簇恢复加外键 |
| 三大日志 | Undo 回滚 Redo 存，Binlog 主从要区分 |
| 日志类型 | Redo 物理，Binlog 逻辑 |
| 索引查询 | 二级索引存主键，覆盖索引不回表 |
| 事务提交 | 先 Undo，再 Redo，Binlog 中间做协调 |

终极一句话：

> MySQL Server 层负责 SQL 的解析、优化、执行；InnoDB 负责数据存储、事务、锁、MVCC、崩溃恢复；Buffer Pool 加速内存访问；Redo / Undo / Binlog 分别保障持久性、回滚、主从一致性。
